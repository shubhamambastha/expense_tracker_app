# Design: Guest Mode (Local-Only, No Login)

Generated by /office-hours on 2026-08-23
Branch: main
Repo: expense_tracker_app
Status: APPROVED
Mode: Builder

## Problem Statement

Today `AuthGate` has exactly three phases — splash → login → app — and the only way to reach `app` is a non-null Auth0 session (`AuthService.instance.currentSession != null`). There is no way to use the app without completing Auth0 login first. We want a "Continue as guest" path that skips Auth0 entirely, with all data persisted on-device only (no Supabase, no cloud), so a user can start logging expenses immediately with zero signup friction.

## What Makes This Cool

Zero-friction first use: capture an expense the moment it happens, no signup wall in between. The independent second-opinion review flagged `ios/AddExpenseWidget/` (the home-screen widget that deep-links into add-expense) as a stretch opportunity — today it still needs a live Auth0 session + network round trip to persist anything. Guest mode is the first execution path in this app with zero network dependency; making the widget guest-capable (log an expense from the lock screen, no signup, no network) is a genuine differentiator, called out as optional stretch scope rather than core.

## Constraints

- Dark-theme-only, no state-management framework (`ChangeNotifier`/`ValueNotifier` singletons + local `setState`).
- Design tokens only — no hardcoded colors/spacing/etc.
- Layer rules hold: screens orchestrate, components are UI-only, services are singletons.
- No new backend infrastructure; guest data never touches Supabase or any cloud service.
- No new dependency — `shared_preferences` is already declared and unused for structured data.

## Premises

1. Guest mode is local-storage-only — no background sync engine. Data lives on-device until the user either keeps using guest mode or logs in. Migration is offered exactly once, at the moment of the first real login after guest data exists; if declined, the local data is retained (not deleted) and can be pulled in later manually from Settings, rather than being re-prompted on every subsequent login.
2. The auth boundary (`AuthGate`/`AuthService`) is the right place to introduce a "guest" identity state, rather than threading a new flag through every screen. Concretely: `AuthService.instance.isGuest` (`ValueNotifier<bool>`), persisted to SharedPreferences (same mechanism `SplashBootstrap` already uses for the onboarding-complete flag) so it survives a process kill — `_AuthPhase` itself is unchanged, but both `SplashBootstrap._resolveLoggedOutDestination` (cold start) and `AuthGate`'s runtime routing check `isGuest` the same way they check `currentSession`, and route to `app`/`dashboard` when either is true.
3. Screens/components, and the CRUD calls inside cross-cutting singletons (`CategoryCatalog`, `IncomeCategoryCatalog`, `CategoryBudgetService`, `CurrencySettings`, `SettingsPreferences`), all keep calling one data-access interface (`SupabaseService`) regardless of guest vs. logged-in — none of them need to branch on which backend is active, because `SupabaseService` does it once. Concretely: `SupabaseService` gains a single choke point, `static bool get _isGuest => AuthService.instance.isGuest.value`, and every existing public method (including `setTransactionPaused`/`setTransactionClosed`, `resetUserData`, and everything else currently gated by `requireUserId()`) becomes `if (_isGuest) return GuestStore.x(...); final userId = requireUserId(); ...` — one pattern applied uniformly, not a bespoke branch per method. This premise does NOT cover `AuthGate`'s separate session-change *sync orchestration* (`_syncUserPreferences`/`_clearUserScopedState`, which decides *when* to trigger a `syncForUser(userId)` pull) — that's auth-lifecycle plumbing, not data access, and is addressed in Next Steps #1.

## Cross-Model Perspective

Independent Claude subagent cold read (Codex unavailable):

- **Coolest version**: make `AddExpenseWidget` guest-capable — log an expense from the lock screen, in airplane mode, before ever creating an account. No competitor onboarding flow does this.
- **Delight signal**: the widget's mere existence in this codebase shows the team already decided capture-latency-at-the-moment-of-spending is the core value, not after-the-fact reconciliation — guest mode's win condition is "the widget works before login exists."
- **Storage hypothesis check**: confirmed SharedPreferences JSON blobs (no new DB dependency) as sound for this app's shape — `fetchTransactions()` already loads everything unpaginated and filters in Dart, so a blob just moves that cost earlier, it doesn't introduce a new class of problem. The general 2026 "use Drift" advice targets apps needing joins/complex queries/sync-conflict resolution, which this app has none of. **Real gap identified**: `Transaction.id` is server-assigned `int?` — guest mode needs its own local ID scheme (negative ints from a local counter, discarded on migration since replay-through-insert gets fresh server IDs). Also: each collection (transactions/accounts/categories/etc.) needs its own SharedPreferences key, not one giant blob, so a single write doesn't rewrite everything.
- **Foreign keys survive the ID swap, but only if remapped**: `Transaction.accountId`/`transferToAccountId` and `RecurringEvent.transactionId` are `int` FKs into locally-generated negative IDs while in guest mode. Migration must replay parents before children and rewrite each child's FK from the old local ID to the new server-assigned ID via an in-memory old→new map — this is real logic, not just "discard the local ID." `category` fields, by contrast, are plain strings and need no remapping.
- **Default categories will collide on migration if replayed blindly**: `ensureDefaultCategories`/`ensureDefaultIncomeCategories` dedupe by lowercase name, and a real account gets these same defaults seeded independently. Since guest sessions are seeded with identical default names (Next Steps #2), migration must match category/income-category (and account) rows by name against what the target account already has, reuse the existing row's ID in the old→new map, and only insert rows that are genuinely new — not blindly re-insert every local row.
- **Build order**: (1) AuthGate guest path first — everything else plugs into it. (2) `GuestStore` + branch the 4 core transaction methods, prove add-expense-as-guest end to end before touching the rest. (3) Mechanically repeat the branch for the remaining collections. (4) "Continue as guest" entry point + migration flow, last — meaningless without 1-3 working.

## Approaches Considered

### Approach A: Branch inside the existing `SupabaseService` facade (chosen)
Add a guest session state to `AuthService`/`AuthGate`; new `GuestStore` class (SharedPreferences JSON per collection, local negative-ID counter); each `SupabaseService` static method branches guest-vs-real internally. Zero changes required to the 6 screens/entry points or 5 singleton services that already call it (11 call sites total, verified by grep).
- Effort: M · Risk: Low-Med
- Reuses: `SupabaseService`'s existing static-facade choke point (verified as the sole call site for `Supabase.instance.client` in the codebase), existing `toMap()`/`fromMap()` on every model, existing `shared_preferences` dependency, existing `feature_flags.dart` pattern.

### Approach B: Extract a `DataRepository` interface
Convert `SupabaseService`'s static API into an injectable interface with `SupabaseRepository`/`LocalRepository` implementations; swap all 11 existing call sites to go through it.
- Effort: L-XL · Risk: Med
- Rejected: bundles a structural refactor (static → injected, across every call site) into this feature for a second-backend need that doesn't exist on the roadmap. Cleaner long-term but not justified by the actual ask.

### Approach C: In-memory only, no persistence
Guest mode as a session-only "try before you sign up" demo, cleared on app close.
- Effort: S · Risk: Low
- Rejected: contradicts the explicit requirement that guest data be saved locally and survive restarts.

## Recommended Approach

**Approach A.** Smallest diff that fully satisfies the stated requirement (local, persistent, no-login usage) without introducing a new dependency or restructuring the existing data-access pattern. `SupabaseService` remains the single facade every caller already uses; the guest/real branch lives inside it.

## Open Questions

- Any user-facing warning that guest data is device-local only and can be lost on uninstall/reinstall?

## Success Criteria

- "Continue as guest" reachable from the login screen, alongside (not replacing) Auth0 login.
- A new guest session starts with the same default categories/income categories a new real account gets (`ensureDefaultCategories`/`ensureDefaultIncomeCategories` today) — not an empty picker.
- A guest can add/edit/delete transactions, accounts, categories, income categories, and category budgets; all persist across app restarts with zero network calls.
- "Reset My Account" in Help Center works for a guest: clears the local `GuestStore` instead of calling `SupabaseService.resetUserData()`.
- Logging in for real after guest use offers a reviewable migration ("N transactions, date range, total — bring these in?") before replaying local data into the authenticated account. Migration is all-or-nothing: on any failure mid-replay, local guest data is left untouched and the user can retry; nothing is partially imported.
- Local guest data is cleared only after migration fully succeeds (or the user explicitly discards it).

## Distribution Plan

Existing app store deployment pipeline covers this — no new distribution channel needed.

## Next Steps

1. `AuthService.isGuest` (`ValueNotifier<bool>`, backed by a persisted SharedPreferences flag) behind a new `FeatureFlags.guestModeEnabled = true` constant (same non-instantiable-class/`static const bool` pattern as `transferVisible` — a one-line kill switch, not a rollout gate). Wire it into cold start (`SplashBootstrap._resolveLoggedOutDestination` routes to `dashboard` when `isGuest` was persisted true, same as it does for a valid session) and runtime routing — `AuthGate` registers a second listener, `AuthService.instance.isGuest.addListener(_onGuestChange)`, in `initState` (mirroring the existing `_onSessionChange` pattern), treating `isGuest.value == true` the same as a non-null session for reaching `app`. In `AuthGate._syncUserPreferences` (session-change *sync-orchestration*, not the data-access layer — see Premise 3): for `CurrencySettings`/`SettingsPreferences`, the guest branch skips their remote-pull step (both already persist every change to a local SharedPreferences key independent of sync, so nothing is lost). For `CategoryCatalog`, `IncomeCategoryCatalog`, and `CategoryBudgetService`, sync is **not** skipped — `syncForUser`/`refresh()` must still run for guests, because that's the only code path that reloads their in-memory `_categories`/`_budgets` state on cold start; skipping it would silently empty those lists on every restart even though the underlying rows are safe in `GuestStore`. Calling `syncForUser`/`refresh()` for a guest is safe and correct because it routes through the already-branched `SupabaseService` methods (`ensureDefaultCategories`, `fetchCategoryBudgets`, etc.) per Premise 3 — no separate guest implementation needed, just don't special-case these three out of the call.
2. `GuestStore` (SharedPreferences, per-collection keys, local negative-ID counter), seeded on first guest session with the same default categories/income categories `ensureDefaultCategories`/`ensureDefaultIncomeCategories` seed for a new real account. Branch the 4 core transaction methods on `SupabaseService` via the single `_isGuest` choke point (Premise 3); prove the add-expense-as-guest loop end to end.
3. Mechanically repeat the branch for the remaining method groups (accounts, categories, income categories, budgets, recurring events, user settings), plus `setTransactionPaused`/`setTransactionClosed` (used by Recurring Payments Manager — call `requireUserId()` directly today, easy to miss since they're not grouped under "transactions") and `resetUserData()` (guest branch clears `GuestStore` instead of deleting Supabase rows — this is a shipped Help Center entry point, not optional). Audit every remaining `requireUserId()` call site while doing this pass to make sure none are missed.
4. Guest sign-out: `AuthGate._signOut()` gains an `isGuest` branch — for a guest, skip `AuthService.instance.logout()` entirely (there is no Auth0 session to close), just clear the persisted `isGuest` flag and route to `login`, leaving `GuestStore` data untouched (so re-entering guest mode later resumes where they left off, consistent with declined-migration behavior below). A guest converts to a real account by signing out (this step) and then logging in normally — the existing `_onSessionChange` → `_handleSignedIn` plumbing fires exactly as it does today.
5. Migration flow, triggered inside `AuthGate._handleSignedIn`, before `_syncUserPreferences` runs: if `GuestStore` has data, show the reviewable-diff confirm dialog ("N transactions, date range, total — bring these in?") before replaying. Replay order is accounts → categories/income categories → transactions (rewriting each `accountId`/`transferToAccountId` from local negative ID to the new server ID via an in-memory old→new map) → recurring events (same remap for `transactionId`) → category budgets. Category/income-category/account rows are matched by name against what the target account already has before inserting (see Cross-Model Perspective) — only genuinely new rows get inserted. **User settings are excluded from migration** — only replayed if the target account has no existing `user_settings` row yet (i.e. this is genuinely a first-ever login); otherwise skipped entirely, since `upsertUserSettings` overwrites wholesale and settings aren't worth risking clobbering an existing account's preferences over. **Rollback on failure**: any failure mid-replay deletes every row inserted so far in this attempt (via the old→new ID map, in reverse dependency order: recurring events → transactions → category budgets → accounts/categories) using the existing `SupabaseService` delete methods, then surfaces a retry option — `GuestStore` itself is never touched until a full replay succeeds.
6. Deferred action: if the user declines migration at login, add two Settings entries visible only while leftover `GuestStore` data exists — "Import guest data" (manually triggers the exact same replay+rollback logic from step 5) and "Discard guest data" (clears `GuestStore` with no network calls, no replay).
7. *(Stretch, optional)* `AddExpenseWidget` guest-capable path.
