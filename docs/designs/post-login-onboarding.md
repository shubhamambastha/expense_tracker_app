# Design: Post-Login Onboarding Wizard

Generated by /office-hours on 2026-08-23
Branch: main
Repo: expense_tracker_app
Status: APPROVED (real-login path) / PENDING ASSIGNMENT (guest-mode path — Outside Voice T3: architecture was locked before the Assignment validated Premise #2; the wizard can be built and shipped for real logins now, but shipping to guest mode is blocked until the Assignment actually runs)
Mode: Startup

## Problem Statement

New users — real Auth0 sign-ups and guest-mode entries alike — land directly on an empty dashboard with generic defaults (default currency, no budget, no recurring expenses configured). The founder left Mint/YNAB over bad UX and premium paywalls and built this app instead; they use it daily and know at least one other person with the same frustration. There's currently no first-run flow that captures identity, currency, a budget target, an income baseline, or known recurring expenses before the user starts using the app blind.

## Demand Evidence

"I built it for myself and use it daily" — founder is the primary user, real n=1 daily-use behavioral evidence. Narrow but real: self-use is a legitimate (if early) demand signal.

## Status Quo

Previously used a mainstream app (Mint/YNAB/bank app), left because of "mostly bad UX and need to pay for premium features" — friction in daily logging plus paywalled functionality, not a missing category of feature.

## Target User & Narrowest Wedge

"A specific friend/family member with the same frustration" — a second named human beyond the founder, same two pain points (bad UX, paywall). Q4 (narrowest wedge) was not asked — smart-routed out at pre-product stage per the skill's stage-based question set (Q1/Q2/Q3 only).

## Constraints

- Dark-theme-only, no state-management framework (`ChangeNotifier`/`ValueNotifier` singletons + local `setState`).
- Design tokens only — no hardcoded colors/spacing/fonts.
- Layer rules hold: screens orchestrate, components are UI-only, services are singletons.
- Auth0 login + Supabase persistence already wired; guest mode (on-device, `GuestStore`) shipped same day as this session.
- Routing chokepoint is `AuthGate` (`lib/components/common/auth_gate.dart`) — `_AuthPhase` enum (`splash | login | app`), with `_handleSignedIn()` (real login) and `_handleGuestEntry()` (guest mode) both currently jumping straight to `app`.
- Reusable pieces already shipped: `SettingsPreferences.displayName` (pre-fillable from Auth0 session name), `SettingsPreferences.monthlySpendingLimit` (overall monthly budget, currently only settable from `budgets_and_spending_page.dart`), `CurrencySettings` + `user_settings.default_currency_code`, `showAddRecurringSheet` in `add_recurring_sheet.dart` (a `showModalBottomSheet` helper that only picks a `RecurringKind`; the caller then pushes `AddTransactionPage` preconfigured for that kind — see Section 1 architecture finding) + `subscription_catalog.dart` (recurring/subscription creation), `IncomeFlowHelpers.applyCategoryRecurringDefaults` (returns a `RecurringConfig` default given a category name, used to pre-seed `AddTransactionPage` for the income step), `AddTransactionPage`'s decoupled `onSave` callback + built-in "save and add another" (`add_transaction_page.dart:64,434`) — the actual reuse mechanism for both income and recurring steps, wired to `SupabaseService.insertTransaction`, no bespoke forms needed.
- **REVERSED per eng-review outside voice (T5eng):** the completion flag does NOT live in `UserSettings.preferences` jsonb. Verified: `SettingsPreferences.preferencesToJson()` (`settings_preferences.dart:351-378`) is a hardcoded fixed-key map that does not include `onboarding_completed_at` — its own routine debounced remote sync (any theme/haptics/notification toggle anywhere in Settings) calls `upsertUserSettings(preferences: ...)` with that fixed map, which **replaces the whole blob** (`supabase_service.dart:432-448`), silently dropping the flag the very next time the user touches any unrelated setting. A fetch-merge-write on the wizard's OWN write (the original 2B fix) only protects that one write — it doesn't protect against `SettingsPreferences`' subsequent unrelated syncs. Fix: a dedicated `user_settings.onboarding_completed_at timestamptz` column (small migration — `SettingsPreferences` only ever touches the `preferences` sub-map, never top-level columns, so this is immune to the clobbering bug). Guest accounts get their own local flag in `GuestStore` (see Open Question #2, reopened).
- No user-declared "monthly income" field exists today — `monthlyIncome` is always computed live from logged transactions (`expense_home_page.dart::_currentMonthIncome()`).
- A separate, unrelated, currently-dead `SplashDestination.onboarding` enum exists in `splash_bootstrap.dart` for a *pre-login* first-launch experience (`docs/BACKLOG.md:15`). This is a different concept from the post-login questionnaire scoped here and must not be conflated with it — not repurposed, because it lives in a different auth phase entirely (`SplashBootstrap`'s pre-login routing vs `AuthGate`'s post-login phase machinery) and represents a different first-launch concept, not "financial profile complete." Three distinct onboarding-shaped keys now exist in the codebase (this dead enum, `SplashBootstrap`'s dead `onboarding_complete` SharedPreferences key, and this feature's new `financial_profile_onboarding_complete`) — Outside Voice flagged this as a future-confusion risk; the distinct names and this explicit note are the mitigation, not a shared key.
- Wizard step writes follow the same "best-effort, non-blocking" precedent `SplashBootstrap.completeDeferredSync` already establishes for exactly this class of problem (Outside Voice finding) — no write blocks the UI thread or advancing to the next step (Open Question #8).

## Premises

1. The wizard asks all 5 categories (identity, income, budget, recurring expenses/subscriptions, currency) up front, rather than a minimal 3-question version — **kept** after being shown 2026 fintech-onboarding research (2-3 questions max before drop-off, defer the rest). Resolution: keep 5, but reuse existing components inline for the income/recurring steps rather than building parallel forms.
2. The wizard blocks **both** real Auth0 login and guest-mode entry — **kept** even after the cross-model second opinion flagged that this directly contradicts the guest-mode design doc written hours earlier ("zero-friction first use... no signup wall in between"). No new reasoning was supplied when this was re-confirmed — flagged as an explicit, currently unresolved risk rather than a reasoned defense (see Open Questions).

## Cross-Model Perspective

Independent Claude subagent cold read (Codex unavailable):

- **Strongest version**: not "an onboarding questionnaire" but "seed the budget math on day one instead of after 30 days of logging" — personalizing around real recurring cash flow (declared income + subscriptions) instead of waiting for computed numbers to populate.
- **Most revealing answer**: Q3's "a specific friend/family member with the same frustration" — evidence for *removing* friction, not adding a gate, per the subagent's read.
- **Challenged premise**: #2 (guest-mode gating). The guest-mode design doc's explicit differentiator was zero-friction entry; gating it with a 5-question form reintroduces the exact signup wall guest mode was built to delete, for a user who by construction hasn't decided to trust the app yet. No production data exists yet either way (pre-launch, n=2 known users) — the subagent's read is that premise #2 was agreed on vibes, days after research said do the opposite.
- **48-hour build**: only gate real Auth0 login, not guest mode; cut to 3 questions (name, budget, currency); reuse existing components; insert a single `_AuthPhase.onboarding` between `login` and `app` in `_handleSignedIn()` only.

The founder held both premises after seeing this challenge (see Premises above).

## Approaches Considered

### Approach A: Minimal wizard, reuse everything
New `_AuthPhase.onboarding` + 5-step wizard. Name/budget/currency write directly to existing `SettingsPreferences`/`CurrencySettings`. Recurring-expenses step invokes the existing `showAddRecurringSheet` modal repeatedly via a "list + add another" pattern (see Constraints — it's a `showModalBottomSheet` helper, not an embeddable widget). Income stored as a new display-only `preferences` jsonb key (no schema migration), not wired into recurring-income projection. Effort M, risk low.

### Approach B: Ideal architecture — income answer creates a real recurring salary transaction, plus the aggregation fix that actually makes it count every month
Same wizard shell. Both the income step and the recurring-expenses step push the real `AddTransactionPage` (`onSave: Future<void> Function(TransactionDraft draft)`, `add_transaction_page.dart:64`) with `onSave` wired to `SupabaseService.insertTransaction` — no bespoke inline forms. Income: pre-seeded via `IncomeFlowHelpers.applyCategoryRecurringDefaults`'s monthly-frequency config for the Salary category. Recurring: `showAddRecurringSheet` picks a `RecurringKind` first, then pushes `AddTransactionPage` preconfigured for that kind; the screen's own built-in "save and add another" button (`_onSave({required bool addAnother})`, line 434) already handles the multi-item loop — the wizard doesn't build any custom "add another" UI. Both steps need a visible "back to setup" affordance so pushing a full screen mid-wizard doesn't read as leaving onboarding. This reuse is low-risk — it's the same creation path that already works today per `docs/BACKLOG.md`. Completion flag: **small migration** — a dedicated `onboarding_completed_at timestamptz` column on `user_settings` for real accounts (reversed from the jsonb-only plan per eng-review outside voice — `SettingsPreferences`' own routine sync clobbers unknown `preferences` keys, a real column is immune), plus a local flag in `GuestStore` for guest accounts. Insertion point: a new `_AuthPhase.onboarding` between `login` and `app` in `AuthGate`, entered from `_handleSignedIn()` (and `_handleGuestEntry()` per Premise #2).

**Correction from adversarial review, revised per Outside Voice (T2):** creating the recurring transaction does NOT by itself close the BACKLOG "recurring income not projected forward" gap — `DashboardAggregations.monthIncome` only sums transactions dated in the current month, so a salary transaction created today still silently drops out of the Income figure next month exactly as BACKLOG describes. Closing the gap requires the separate aggregation fix BACKLOG.md already recommends: `monthlyRecurringIncomeTotal` mirroring `monthlyRecurringExpenseTotal`, plus a `!t.isRecurring` exclusion added to `monthIncome` itself (Outside Voice T1 — without it, the wizard's own income transaction double-counts in its creation month). Approach B has two deliverables, (1) wizard income step → existing transaction-creation path and (2) the aggregation fix, but **they ship together, same PR/branch** — the outside voice correctly flagged that shipping (1) alone (behind a still-pending (2)) gives Approach B's income step zero functional advantage over Approach A's display-only field, while costing more UI complexity (a full-screen `AddTransactionPage` push) for nothing. Effort L, risk medium — (2)'s double-counting fix is now precisely specified (Open Question #5), not just flagged.

### Approach C: Single scrollable profile-card screen instead of a paginated wizard
All 5 inputs on one screen with collapsible cards and a single CTA, instead of 5 sequential screens with progress dots. Cheapest to build UI-wise, sidesteps the "feels like a form" friction call-out from the onboarding research. Effort S/M, risk low.

**Not chosen — reasoned rebuttal:** two of the five steps (recurring expenses, and the income step's category/frequency picker) reuse existing full-screen or modal-sheet UI (`showAddRecurringSheet`, `add_transaction_page.dart`'s income form) that isn't designed to collapse into a card on a shared scroll view without a real rebuild — a single-screen layout would mean re-implementing those interactions in miniature rather than reusing them as-is, undercutting the reuse thesis both A and B depend on. A paginated wizard also gives an explicit "3 of 5" progress signal, which matters more for a 5-step flow than for the research's baseline 2-3-question case it was measuring drop-off against. This is a real trade-off, not a dismissal — if Open Question #1's observation shows people bouncing off the step count itself rather than any individual step's content, Approach C becomes the right fallback and should be revisited then, not before.

### Approach D: No hard gate — progressive/deferred prompts after first guest use (Outside Voice finding, documented not adopted)
Never explored during Phase 4 — only wizard *shape* (A/B/C) was considered, not whether gating guest mode should exist at all. Instead of blocking "Continue as guest" with the wizard, let guests reach the dashboard immediately (true zero-friction, matching `docs/designs/guest-mode.md`'s stated goal), then show dismissible, contextual prompts after they've gotten real value — e.g. a "set your budget?" banner after their first logged expense, one prompt at a time, skippable, never a blocking screen. Gets most of the personalization benefit without reintroducing the signup wall guest mode was built to remove. **This is the fallback to build if the Assignment (Premise #2's validating experiment) shows guest-mode gating hurts real usage** — documented now so it doesn't need rediscovering later. Real login still gets the full wizard (Approach B) regardless of this outcome, since login already implies the user has committed to the app.

## Recommended Approach

**Approach B**, chosen by the founder, corrected per adversarial review and Outside Voice: two deliverables — (1) the wizard's income step calling the app's existing transaction-creation path, and (2) the `monthlyRecurringIncomeTotal` aggregation fix (plus the `!t.isRecurring` exclusion on `monthIncome`, Open Question #5) that makes a declared income answer count every month, not just the month it's created — **shipping together, same PR/branch** (Outside Voice T2: shipping (1) without (2) gives zero functional advantage over Approach A while costing more UI complexity). Reuses existing UI components for name/budget/currency/recurring.

## Accepted Expansions (SELECTIVE EXPANSION, /plan-ceo-review)

Cherry-picked during the CEO scope review, now part of plan scope for all remaining sections:
0. **Minimal local wizard analytics** (built now, not deferred) — `SharedPreferences` counters for wizard started/completed/skipped-per-step, inspectable via a debug menu. This app has zero product analytics anywhere (Open Question #10); without this, the Assignment's one manual observation is the only data this feature will ever get at scale.
0b. **Persistent progress context across full-screen pushes** (built now, not deferred, and promoted to P1 per design-review outside voice — the whole rationale for a paginated wizard over Approach C depends on this) — the "step X of 5" indicator must visually persist or be clearly resumed across the two `AddTransactionPage` pushes (income, recurring), which otherwise show their own AppBar/chrome with no wizard context.
1. **Live budget preview** — the budget step shows a live preview of the existing Spending Room card as the user types, instead of a blind numeric field. Reuses the existing widget. **Accessibility (Pass 6):** the preview value must be wrapped in `Semantics(liveRegion: true, ...)` so screen readers announce the updated figure on change, not just render it silently — DESIGN.md's "never communicate state with color/visual alone" principle applied to a dynamic value.
2. **Locale-based currency pre-fill** — the currency step pre-selects from device locale instead of defaulting blank, reducing it to a one-tap confirm for most users. Falls back to a safe default (USD) when the device locale doesn't map to a supported currency code (Section 4 edge case).
3. **Trust microcopy on the income step** — split by path for accuracy (Section 3 finding): guest mode shows "stays on this device, never shared" (literally true, `GuestStore` is on-device only); real login shows "stays on your account, never shared with anyone else" (accurate — it syncs to Supabase, scoped privately, not "on device"). The wizard already knows which path it's in, no new branching cost. Addresses the trust hesitation named in Open Question #4, directly tied to the founder's own reason for leaving Mint — an inaccurate privacy claim here would be worse than none.

## Open Questions

1. **Guest-mode gating (premise #2) is unresolved risk, not a settled call.** The founder kept it without new reasoning after a direct, evidence-backed challenge. Before building, watch a real guest-mode entry attempt (see Assignment) — if the friend/family member named in Q3 balks at 5 questions before their first guest expense log, this needs revisiting.
2. **REOPENED (eng-review outside voice, T5eng): `GuestStore` needs its own local completion flag after all**, distinct from the real-account `onboarding_completed_at` column (the unified-jsonb approach was reversed — see Constraints). **Also corrects a factual error**: this question previously recommended migration "carry over" the flag via `GuestMigrationService`, but `GuestMigrationService`'s own doc comment (`guest_migration_service.dart:44-48`) explicitly states "User settings are deliberately excluded — replaying them risks silently overwriting an existing account's preferences." That policy is correct and shouldn't be weakened for this feature. Fix: `AuthGate._maybeOfferGuestMigration`, on successful migration, explicitly sets the real account's `onboarding_completed_at` column directly (a single scoped write, not a change to `GuestMigrationService`'s broader "exclude preferences" policy) if the guest's local flag was already true — so a guest who already answered doesn't see the wizard again post-migration, without touching migration's general preferences-exclusion rule.
3. **RESOLVED at implementation (simpler than originally scoped): backfill, not a read-path special case.** The migration (`sql/20260824_onboarding_completed_at.sql`) explicitly backfills every pre-existing row to `now()` at migration time, flipping the semantics to the standard, unambiguous `NULL = pending`. This avoids the original plan's risk (a brand-new row created after ship would *also* default NULL under a "NULL = complete" scheme, incorrectly skipping onboarding for new users too) and removes the need for any special-case read-path logic — `onboardingCompletedAt == null` just means "show the wizard," full stop.
4a. **RESOLVED (Section 4 finding): hardware back button is blocked during the wizard**, matching `AuthGate`'s existing `PopScope(canPop: _phase == _AuthPhase.app)` — the onboarding phase inherits `canPop: false` like splash/login already do, no new logic needed. Only in-UI Skip/Back buttons move between steps.
4. **Skip semantics.** Every step should be skippable per the onboarding research (deferred answers should be gettable later from Settings/the Recurring Payments Manager) — needs explicit UI treatment per step, not just an overall wizard skip.
5. **RESOLVED (Outside Voice finding, T1): the actual fix, not just the risk.** `monthIncome` (`dashboard_aggregations.dart:62-70`) currently sums by date with no recurring exclusion — verified against `discretionaryMonthSpend` (line 132-147), which excludes `!t.isRecurring` (plus two category-based clone exclusions specific to the expense-side "Mark paid" flow that don't apply here — deliverable 2 is projection-only, no clone/ledger materialization, per BACKLOG's own (a)/(b) split). Fix: add `!t.isRecurring` to `monthIncome`'s filter (mirroring `discretionaryMonthSpend`'s first exclusion clause), and add the new `monthlyRecurringIncomeTotal` (mirroring `monthlyRecurringExpenseTotal`) as a separate figure summed alongside the now-corrected `monthIncome` — the same composition pattern `spendableToday` already uses on the expense side. Without the `!t.isRecurring` exclusion, the wizard's own income transaction is counted twice in its creation month: once by the literal date-sum, once by the projection. **Confirmed (eng-review outside voice, T5eng): `expense_home_page.dart:677-684`'s `_currentMonthIncome()` is a SEPARATE inline implementation** (filters `_transactions` locally, does not call `DashboardAggregations.monthIncome`). **Fix: consolidate** — replace `_currentMonthIncome()`'s body with a delegation to the corrected `DashboardAggregations.monthIncome` (+ `monthlyRecurringIncomeTotal`), removing the duplicated logic entirely rather than patching both independently. One implementation to fix, not two to keep in sync.
6. **RESOLVED (Section 2 error-map finding).** Full order: `_maybeOfferGuestMigration` → `_syncUserPreferences` → wizard → `_AuthPhase.app`. Migration runs first so the wizard can pre-fill from migrated guest data; `_syncUserPreferences` runs before the wizard specifically so `CategoryCatalog.syncForUser`/`ensureDefaultCategories` have already created default expense/income categories by the time the wizard's income/recurring steps push `AddTransactionPage` — otherwise a brand-new user would see an empty category picker mid-wizard.
7. **Resume/interruption behavior.** If the app is killed mid-wizard, is the completion flag only written on full completion — meaning a killed session re-prompts from question 1 — or is partial progress persisted per step? Recommend: write the flag only on full completion or explicit skip-all; no partial resume for the 3 simple field steps (name/currency/budget). The income/recurring steps have their own idempotent-resume guard — see Open Design Question D2.
8a. **RESOLVED (eng-review outside voice, T5eng): no re-entrancy guard on `_handleSignedIn`/`_handleGuestEntry`** (confirmed by grep — no `_isHandlingSignIn`-style flag exists today). Latent today because both run fast; this plan inserts an interactive, multi-minute wizard, so a second session-change notification mid-wizard (Auth0 silent token refresh, app foreground) could re-enter and re-run migration-offer/sync concurrently with the wizard in flight. Fix: a simple in-flight boolean set at entry, checked at entry, cleared on completion — matches the existing `_phase != _AuthPhase.splash` early-return pattern already used in this file for `_onSessionChange`/`_onGuestChange`.
8. **Per-step write failures.** Each step's write (name → `SettingsPreferences`, budget → same, currency → `CurrencySettings`, income → transaction insert, recurring → `AddTransactionPage`'s own insert) should be independent — a failed write on one step, from **any cause (network timeout or local write failure, e.g. `SharedPreferences` disk-write exceptions)**, shouldn't block advancing to the next step or reaching the dashboard. Needs an explicit "best-effort, don't block on sync" statement in implementation, not silent assumption.
9. **RESOLVED (Section 4 finding), updated for the T5eng column reversal: local-first flag is required for BOTH paths, not optional.** Real accounts: a local `SharedPreferences` cache (key: `financial_profile_onboarding_complete` — distinct from `SplashBootstrap`'s existing `_kOnboardingCompleteKey = 'onboarding_complete'`, `splash_bootstrap.dart:87`, per the collision risk noted here) written synchronously the moment the wizard completes, so an offline completion still doesn't re-show the wizard next launch while the `onboarding_completed_at` column write happens best-effort in the background. Guest accounts: `GuestStore`'s own local flag (Open Question #2, reopened) IS the local-first store — no separate cache needed there, it's already fully local. Collision risk: reusing `onboarding_complete` would silently corrupt both this feature's and `SplashBootstrap`'s unrelated pre-login routing the moment either is read.
10. **No product analytics/crash reporting exists anywhere in this app** (verified — the only "analytics" hits in the codebase are in-app financial analytics, not usage telemetry). This is a pre-existing, app-wide gap, not specific to this feature, so it doesn't block shipping — but it means wizard completion/skip/drop-off rate (the exact data Open Question #1's guest-mode risk depends on at scale) can only ever be observed manually, one user at a time, as the Assignment describes. Worth a one-line note, not a blocker.

## User Journey Storyboard

| Step | User does | User feels | Plan specifies? |
|---|---|---|---|
| 0. Just logged in | Watches a brief pre-fill load | Impatient — they came here to see their money, not wait | Yes — uses `states.dart`'s existing loading pattern, brief single fetch |
| 1. Name | Sees their own name already filled in | Recognized, not interrogated — "it already knows me" | Yes — Auth0 pre-fill |
| 2. Currency | Sees a currency already selected, likely correct | Relief that this is a 1-tap confirm, not a search | Yes — locale prefill |
| 3. Budget | Types a number, watches a live preview react | Curiosity, then a small "oh, that's what this looks like" moment | Yes — live Spending Room preview (accepted expansion), but see Pass 6 finding below |
| 4. Income | Taps into a full-screen form, different chrome than steps 1-3 | Risk of "wait, did I leave the setup flow?" — the exact break the design-review outside voice flagged | Only partially — T10 (persistent progress context) exists but is new, unbuilt |
| 5. Recurring | Adds 0-N items via a familiar "add another" loop | Either quick relief (skip, nothing to add) or mild fatigue if they have many subscriptions | Yes — the loop is native to `AddTransactionPage`, no new fatigue introduced beyond what already exists elsewhere in the app |
| 6. Dashboard | Arrives at a dashboard that already reflects their real numbers | The payoff moment — "it already knows my budget" instead of a blank slate | Yes — this is the whole thesis of the feature (Problem Statement) |

**5-second visceral:** step 0-2 (fast, recognized, low-effort). **5-minute behavioral:** steps 3-5 (the actual work, where drop-off risk concentrates — this is exactly what the Assignment is designed to observe). **5-year reflective:** step 6 onward — does a user look back and think "that setup was worth it" the first time `spendableToday` shows an accurate number without them having logged 30 days of transactions first.

## Wizard Shell Visual Spec (Pass 4/5 completeness fix)

Progress indicator: thin linear progress bar, `AppColors.primary` fill on `AppColors.surfaceSecondary` track, positioned above the heading per the User Flow diagram — not a dot-stepper (dots don't communicate "3 of 5" as precisely for a 5-step flow). Buttons: `Skip` as a text button (`AppColors.textSecondary`, no fill), `Next`/`Done` as a filled primary button (`AppColors.primary` fill, `AppRadii.button` = 16px radius, per `AppTextStyles.button`). Step transitions use `AppDurations`/`AppCurves` tokens (whatever the app's existing page-transition values are — matching `AuthGate`'s own `AnimatedSwitcher` transition, not a new motion language). No cards for the name/currency/budget steps beyond the existing Spending Room preview card and the input field itself — per App UI rules, cards only where the card IS the interaction (the live preview is a real dashboard widget, not decoration).

## Open Design Questions

1. **RESOLVED (D2): idempotent resume for income/recurring steps.** If the app is killed after the income/recurring steps already created real transactions but before the completion flag is set, a naive restart-at-step-1 (Open Question #7) would re-offer those steps and risk duplicate transactions. Fix: before pushing `AddTransactionPage` for the income or recurring step on any entry (fresh or resumed), check whether a wizard-created transaction already exists for that slot (e.g. a Salary transaction tagged from this flow) and skip re-offering that specific step if so — the other 3 steps (name/currency/budget, all simple field writes, not transaction creation) keep the simple "no partial resume" model unchanged.
2. **RESOLVED (7A): hybrid navigation.** Steps 1-3 (name/currency/budget) live in one inline `PageView` within `OnboardingWizardPage` — the progress bar animates smoothly between them, no route-transition overhead for lightweight field steps. Steps 4-5 are necessarily separate pushed routes since they reuse the existing `AddTransactionPage` screen. The persistent progress header (T10) unifies both halves so the transition between PageView and pushed routes doesn't read as leaving the wizard.
3. **RESOLVED (7B): back = Skip.** Backing out of `AddTransactionPage` without saving on the income/recurring steps behaves identically to tapping the explicit "Skip" button — one code path, both leave that step's data unset and advance. No separate "back stays on step" behavior.

## Success Criteria

- A new user — real login or guest, per Premise #2 — sees the wizard exactly once; a returning user (pre-dating this feature or already completed) never sees it again, in either path.
- Every step is individually skippable; skipping never blocks reaching the dashboard. No partial-progress resume for the 3 simple field steps — a killed session re-starts from question 1 (Open Question #7). The income/recurring steps are idempotent on resume (Open Design Question D2) — they never duplicate a transaction already created in a prior attempt.
- The income answer, if given, shows up correctly in the month it's created via the existing transaction-creation path, AND continues to fold into the dashboard's Income figure every month after via a sibling `monthlyRecurringIncomeTotal` method (Approach B deliverable 2, mirroring `monthlyRecurringExpenseTotal`), summed alongside `monthIncome()` itself (which gets a `!t.isRecurring` exclusion added, mirroring `discretionaryMonthSpend`'s pattern) — without double-counting against any other income source. `expense_home_page.dart`'s duplicate `_currentMonthIncome()` is consolidated to delegate to the corrected `DashboardAggregations.monthIncome`, not patched separately.
- Currency and budget answers are visible in Settings immediately after the wizard, with no separate "confirm" step needed there.
- Guest-mode gating (Premise #2, kept without new reasoning) has been observed with at least one real person going through the "Continue as guest" entry specifically (the Assignment) before this ships to guest mode — this is a precondition on shipping the guest-mode half of Premise #2, not a nice-to-have.

## Post-Implementation Fixes (found via actual use, not review)

Two real UX gaps surfaced only after building and using the wizard — neither review caught them because neither review ran the actual flow:

1. **Income was an unnecessary extra screen.** The original plan pushed `AddTransactionPage` for the income step, same as recurring. But income is one number — pushing a whole separate form for it is friction the design doesn't need. Fixed: income is now inline on its own step (same pattern as budget), saved directly on Next, no push, no extra tap.
2. **No way to add accounts before income/recurring needed one.** The wizard went straight from budget into income/recurring without ever giving the user a chance to add a bank account or card — so the first two transactions created had nothing to attach to. Added a new step 4/6, "Add your accounts," before income and recurring, using the same `showAddAccountDialog` the rest of the app already uses. Step order is now: name → currency → budget → **accounts** → income → recurring (6 steps, not 5).

Both required updating `_stepCount`/`_stepIds`/every index reference in `OnboardingWizardPage`, and switching `_accounts` from a plain field to a `ValueNotifier` — the accounts step renders inside a route owned by the nested `Navigator`, whose `onGenerateInitialRoutes` only runs once, so a parent `setState()` after adding an account doesn't reliably reach it. A `ValueListenableBuilder` subscribes directly instead.

3. **No way to go back a step.** Open Question #4a's own resolution said "only in-UI Skip/Back buttons move between steps," but only Skip was ever built. Added a top-left back button (`Icons.arrow_back_rounded`, matching `TransactionAppBar`'s existing convention) to `OnboardingStepScaffold`, wired to a `_goBack(index)` method in the wizard shell. Hidden on step 1 (name) — nothing to go back to, hardware back stays blocked for the whole wizard per 4a.
4. **Recurring step had an unnecessary picker sheet.** Tapping "Add recurring" opened `showAddRecurringSheet` (Subscription/EMI/Other), an extra layer for a choice that could just be made directly on the step. Made the private `_AddRow` in `add_recurring_sheet.dart` public (`RecurringKindRow`) and reused it to list all 3 kinds inline on the recurring step itself — one tap straight into `AddTransactionPage`. `showAddRecurringSheet` itself is untouched and still used by the Recurring Payments Manager's own FAB, a genuinely different context. This also meant the D2 idempotent-resume guard for recurring (`isRecurringStepDone`/`markRecurringStepDone`) no longer applied — it existed to stop an *auto-triggered* push from firing twice, but each kind-row tap is now an explicit user action, and re-visiting the step to add another item is the intended flow, not a duplicate to prevent. Removed; income keeps its guard since that save is still a single per-visit action.
5. **Skip/Next buttons stranded mid-screen on short steps.** `OnboardingStepScaffold`'s outer `Column` had `Flexible(child: SingleChildScrollView(body))` immediately followed by `const Spacer()` — two sibling flex children of equal weight (`flex: 1`). Flutter's `Flex` layout splits leftover space by flex ratio *before* looking at actual content size, so the two competed 50/50 instead of `Spacer` taking 100% of the remainder; on a step whose body was much shorter than half the screen, that left a large empty gap and pushed the button row up into the middle instead of pinning it to the bottom. Fixed by collapsing the back button, heading, subtext, and body into a single `Expanded(child: SingleChildScrollView(...))` — the only flex child left in the `Column` — followed by a fixed `SizedBox(height: AppSpacing.lg)` and the Skip/Next `Row`. Skip/Next now sit at the bottom on every step regardless of content height.
6. **No visibility into what's already been added on the recurring step.** The step only ever showed the 3 "add a kind" rows — nothing told the user what they'd already added this run vs. what was still missing, so re-visiting the step meant guessing or re-opening the app to check. Added an "Added" list above the kind rows: `OnboardingWizardPage._saveTransactionDraft` now captures the `Transaction` `SupabaseService.insertTransaction` returns (previously discarded) and, when `saved.isRecurring` is true, appends it to a new `_recurringItems` `ValueNotifier<List<Transaction>>` — same rebuild-inside-the-nested-Navigator reason as `_accounts`. `OnboardingRecurringIntroStep` renders each item as a read-only row (icon derived from `TransactionSubtypeHelpers.isSubscriptionCategory`/`isEmiCategory`, counterparty name, formatted amount + frequency via `CurrencySettings`/`RecurrenceFrequencyX.label`) styled like the accounts step's existing account rows, distinct from the tappable `RecurringKindRow`s below. Income is unaffected — the income draft's `recurring.enabled` stays false unless the user explicitly turns it on, so it doesn't leak into this list.
7. **Income was silently linked to an arbitrary account.** `_saveIncome` hardcoded `accountId: _currentAccounts.first.id` with no UI to change it — unlike the recurring step, which pushes the real `AddTransactionPage` (a genuine account dropdown), income saved inline with no picker at all, so it landed on whichever account happened to be first (alphabetical from the initial fetch, or first-added if the wizard started with none) regardless of which one the user actually meant. Added a compact account-picker row to `OnboardingIncomeStep` (reusing the existing `SettingsAccountPickerRow`/`iconForAccountType` from `components/settings/settings_picker_helpers.dart`, no new picker UI built) that defaults to the first account but lets the user change it before saving; hidden entirely when there are no accounts, matching the existing silent-skip behavior in that case. `OnboardingIncomeStep.onNext` now passes `(amount, accountId)` instead of just `amount`; `_saveIncome` takes the explicit `accountId` with the old first-account fallback kept only for the null case.
