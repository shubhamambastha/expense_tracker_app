## Problem Statement

Founder left Mint/YNAB over bad UX and premium paywalls and built their own manual-entry expense tracker instead. Question this session: what feature to build next. Diagnostic revealed the founder doesn't currently use their own app as their real money-tracking system ("mostly building, light real usage"), tracks nothing consistently today by any method, and the sharpest evidence of real pain is "chronic anxiety, no hard consequence yet" around not knowing where money goes — a visibility problem, not a discipline problem.

## Demand Evidence

Weak by this framework's own bar. No behavioral evidence (no daily real-money use, no named second user, no financial consequence like an overdraft or missed payment). The one real signal: "chronic anxiety, no hard consequence yet" — an honest, self-corrected answer after being pushed twice, which is itself notable, but it is anxiety-as-symptom, not demand-as-behavior. Treat this design as testing a hypothesis, not shipping a validated feature.

## Status Quo

"Nothing tracked consistently" — no spreadsheet, no bank app, no existing workaround, by the founder or the named-but-unspecified person referenced in Q3. Flagged as a red flag by this framework: if there's no existing (even bad) workaround, the pain usually isn't acute enough to force adoption of a new one either.

## Target User & Narrowest Wedge

No named individual — stayed at "a specific named person" as a category, twice, even when pushed for the actual specifics. Q4 (narrowest wedge) not asked; smart-routed out at pre-product stage.

## Constraints

- Dark-theme-only, no state-management framework (`ChangeNotifier`/`ValueNotifier` singletons + local `setState`).
- Design tokens only — no hardcoded colors/spacing/fonts.
- Manual entry only, held as a firm position after direct challenge: the founder will not add any bank-linking (Plaid-style) or on-device SMS/notification parsing, even after a cross-model second opinion argued these aren't the same constraint as "no third-party credential custodian." No new reasoning was given for holding the line the second time — documented as the founder's call, not re-litigated here.
- No product analytics/telemetry exists anywhere in the app — feature validation is manual, one user at a time.
- `lib/utils/financial_insights.dart::generateInsights()` already exists: a pure, rule-based function producing `FinancialInsight` objects (category delta, weekend spending skew, subscription cost, budget proximity) from `transactions` + `budgets`. Already wired into the Analytics tab only, via `analytics_content.dart` → `behavioral_insights_section.dart` (which already has a reusable "not enough data yet" empty state, `behavioral_insights_section.dart:39-65`, for exactly the thin-data case in Open Question #1). **Correction from adversarial review:** `payment_insights_section.dart` is a separate, unrelated surface with its own private `_Insight` class — it does not call `generateInsights()` and is not existing reuse for this feature.
- `expense_home_page.dart` already owns `_transactions` and budget access, and already handles `FinancialInsight.actionPayload` navigation (`expense_home_page.dart:603`) — wiring a home-tab card in is a small diff on top of plumbing that already exists.
- No local-notifications package in `pubspec.yaml` today — this is a new dependency for any push-based surface.
- `docs/BACKLOG.md` separately documents two already-built-then-removed (2026-08-18) manual-entry-friction features (quick-parse free-text entry, recent-merchant suggestions) — real, reusable code in git history, but a different problem than the one this design targets.

## Premises

1. "The real gap isn't which feature to add next — it's that manual entry is the wrong data-entry model for this app category" — **rejected** by the founder. Reason given: privacy, specifically not wanting a third-party bank API touching user credentials/transaction data, even knowing it costs retention (industry data cited: ~68% higher retention for bank-linked trackers).
2. Cross-model re-challenge: "no bank API" and "no automation" are different constraints — on-device SMS/notification parsing cuts entry friction with zero third-party credential exposure. **Founder held the original position** ("keep manual-only, no exceptions") without new reasoning on the re-ask. Recorded as the founder's explicit choice, not resolved in either direction — see Open Questions.

## Cross-Model Perspective

Independent Claude subagent cold read (Codex unavailable):

- **Strongest version**: a privacy-first, manual-first money *awareness* tool — the product's edge is trust, not convenience, and that's coherent with refusing bank-linking even at a known retention cost.
- **Most revealing answer**: "chronic anxiety, no hard consequence yet" — reframed as a visibility problem, not a budgeting-discipline problem. Nothing in the app today proactively answers "where did my money go this week" — every feature built or removed so far (quick-parse, recent suggestions) attacked entry friction, not this.
- **Challenged premise**: privacy-over-bank-linking as a false binary — SMS/notification parsing or forwarded-email parsing could cut friction with zero third-party credential exposure. Proposed test: ship an on-device SMS parser behind a flag to the founder only for 2 weeks, see if daily use moves from "light" to real. Founder declined to revise on this (see Premises #2).
- **48-hour build proposed**: resurrect quick-parse as on-device SMS/notification-triggered auto-drafted transactions, swipe to confirm.

Not adopted as the recommended approach — the founder's manual-only constraint stands, and Approach B below tests the "visibility, not entry" half of the subagent's read without touching automation at all.

## Approaches Considered

### Approach A: Resurrect entry-friction fixes
Bring back the 2026-08-18-removed quick-parse free-text entry (upgrade the deleted regex `_QuickParser` to a real LLM-backed parser, per BACKLOG's own note) and recent-merchant tap-to-autofill (the income-side data path is already intact and reusable; only the expense-side UI row needs rewiring). Effort S, risk low. Reuses: `quick_ai_input.dart` (in git history), `recentIncomeSuggestions`, `AddTransactionPage`.
**Not chosen — doesn't address the session's actual evidence.** Q3's answer was a visibility gap ("I don't know where money goes"), not an entry-effort gap. This approach makes logging faster without ever telling the user anything new.

### Approach B: Proactive insight digest
Turn `generateInsights()` from a passive Analytics-tab widget into a proactive home-tab card (local notification deferred, see Open Question #2) that leads with the single most relevant insight — "you spent 40% more on dining this weekend" style, using warm, non-judgmental copy. Effort M, risk low-medium. Reuses: `FinancialInsight`, `generateInsights()`, `behavioral_insights_section.dart`'s existing empty state, existing transaction/budget stores, `expense_home_page.dart`'s existing `actionPayload` navigation handling.

**Code quality finding (`/plan-eng-review`):** `behavioral_insights_section.dart:170-248` has a private `_InsightCard` that already implements the exact per-insight UI (tone→color, icon, message, action button) the home card needs. **Decision: promote it to a shared public widget** — move it to `components/common/insight_card.dart` as `InsightCard`, used by both `BehavioralInsightsSection` (Analytics) and the new home-tab card. One implementation, no duplication.

**Outside-voice correction:** `_InsightCard` is built on `AnalyticsSectionCard`, an analytics-namespaced styling wrapper — the promotion is not a pure move. **Decision: decouple.** `InsightCard` gets its own generic, design-token-based container (not `AnalyticsSectionCard`); both `BehavioralInsightsSection` and the new home card wrap it identically. Keeps the promoted widget context-free, which is the actual point of promoting it.

**Outside-voice finding, verified in code:** `expense_home_page.dart:601-607`'s `_handleInsightAction` reads the `filter:category:X` / `budget:X` payload prefix but only calls `_switchToTab(1)` — it never applies the encoded filter. Pre-existing gap, but a proactive home card makes it far more visible (a card promising "See category" that lands on an unfiltered list undercuts the trust this whole feature exists to build). **Decision: fix in the same PR**, not deferred — apply the actual filter when switching tabs, not just the tab index.

**Architecture finding (`/plan-eng-review`):** `HomeContent`'s own class doc comment (`home_content.dart:18-26`) states insights deliberately live on Analytics only, "so home stays scannable." This is a documented precedent Approach B knowingly reverses. **Decision: update the doc comment** (not the code behavior) to state the new intent — a single proactive card on Home leading with the most relevant `generateInsights()` finding, with the full multi-insight list still on Analytics — so the comment matches reality instead of silently going stale. Implementation also needs one new `HomeContent` constructor param (`onInsightAction`, wired to the existing `_handleInsightAction` in `expense_home_page.dart`) — `HomeContent` already computes `budgets` locally (`home_content.dart:85`), so no new prop is needed for that half.

**Two implementation questions the doc must answer, not leave implicit (adversarial-review finding):**
- **Cadence — "weekly" is copy framing only in v1, not a gate.** The card always reflects live-computed state on every app-open; nothing is persisted or throttled. "This week" in the copy just means the heuristics' own lookback window (whatever `generateInsights()`'s category-delta/weekend-skew logic already uses), not a stored last-shown timestamp. A true 7-day gate (persisted `shared_preferences` state) is an explicit v2 option if live-every-open turns out to feel repetitive, not a v1 requirement — added here specifically because leaving it unstated is what let this ambiguity reach an adversarial review undetected.
- **Selection — no ranking function exists in `generateInsights()` today** (it returns its four heuristics in fixed declaration order: category delta, weekend skew, subscriptions, budget proximity; `BehavioralInsightsSection` just takes the first N via `kBehavioralInsightsLimit`). **REVISED (`/plan-eng-review` finding):** v1 originally scoped "first non-neutral-tone result," but `financial_insights.dart` shows weekend-skew (line 134) and subscriptions (line 161) insights are *always* `InsightTone.neutral`, and category-delta (line 100) is only non-neutral above a 35% bump — so "non-neutral-only" would show the empty state instead of a real insight for exactly the low-activity case this feature targets (a real subscriptions insight or a modest category bump). **Decision: v1 takes `generateInsights()`'s first result regardless of tone** (`insights.first`, declaration order: category-delta → weekend-skew → subscriptions → budget-proximity) — a neutral insight is still a real, data-backed finding, not noise. Add a `leadInsight(List<FinancialInsight>)` helper to `financial_insights.dart` rather than inlining the pick in the widget (keeps selection logic testable alongside the generator it reads). Severity-ranked selection (danger before warning before neutral, regardless of declaration order) is the real future work if the fixed order proves wrong in practice — not a blocker to shipping v1.

### Approach C: Weekly check-in (entry + insight combined)
One weekly prompt that surfaces the sharpest insight from `generateInsights()` *and* a one-line quick-add box (reusing/upgrading Approach A's parser) in the same surface — a low-pressure ritual instead of daily logging pressure. Effort M/L, risk medium (combines a new notification surface with a revived parser — more moving parts than A or B alone).

## Recommended Approach

**Approach B**, chosen by the founder. It's the direction actually backed by this session's evidence (the anxiety/visibility gap from Q3) rather than the easiest thing to resurrect from BACKLOG, and it respects the firm manual-entry-only constraint without any workaround.

## Open Questions

1. **RESOLVED (adversarial review): data-thinness empty state already exists, reuse it.** `behavioral_insights_section.dart:39-65` already has a "not enough data yet"-style empty card for exactly this case. The home-tab version of Approach B should reuse that same pattern rather than designing a new one.
2. **Push vs. in-app-only for v1.** A local notification requires a new dependency (`flutter_local_notifications` or similar) plus iOS/Android permission handling; a home-tab card requires none of that. Recommend shipping the home-tab card first (reuses existing app-open behavior, zero new dependencies) and treating push as a fast-follow once the card's insight quality is validated.
3. **Unresolved: is manual-only actually the right call?** The cross-model challenge on privacy-vs-automation was not resolved with new reasoning, just re-affirmed. Not blocking this feature (Approach B needs no automation either way), but flagged as a premise worth revisiting with real evidence rather than re-litigating on vibes, per this framework's own bias against exactly that pattern.
4. **Ostrich-effect risk in copy.** The landscape research named negative-framed dashboards (red overspend banners) as a driver of avoidance behavior. The digest's copy tone — neutral/observational vs. celebratory-when-good/gentle-when-not — needs explicit design attention before shipping, not an afterthought once the mechanism works.

## Sequencing (`/plan-eng-review` outside voice — gates implementation)

**The Assignment below is a validation gate, not a post-approval checklist item — implementation does not start until it clears.** The outside voice's argument: this feature's whole premise is weakly evidenced (see Demand Evidence), and `generateInsights()`'s four heuristics all need month-over-month data or ≥2 active budgets to fire — exactly what a single low-volume user won't have in week one. The cheapest possible test costs zero new code: log a week, then look at what the **existing Analytics tab** already shows today. Only start building `InsightCard`, `leadInsight()`, the home card, and the 4 new test files if that check shows `generateInsights()` genuinely has something meaningful to say for this usage level. If it doesn't, the finding is about the insight engine's heuristics needing more data or different logic first — not "build the UI anyway and hope."

## The Assignment

Before writing any code: open the app right now and manually log every real transaction from today, for one full week, exactly as a real user would. Then open the existing Analytics tab (no new code needed) and read what `behavioral_insights_section.dart` actually shows. If a week of honest logging doesn't produce insights `generateInsights()` can say something meaningful about there, the digest has nothing to prove itself against yet — you'll know before building any new UI whether the insight engine itself needs more heuristics first, or whether this is genuinely ready to build.

## Failure modes

| Codepath | Failure scenario | Test coverage | Error handling | User sees |
|---|---|---|---|---|
| `leadInsight([])` | No insights generated (thin data) | ✓ (approved test plan) | Falls to existing empty-state widget | Clear "log a few weeks..." message, not blank/broken |
| `leadInsight(insights)` first item has `actionLabel == null` | Neutral informational insight with no action | ✓ (InsightCard test, action-absent case) | Renders card with no button | Static card, no dead tap target |
| `_handleInsightAction` gets an unrecognized/malformed payload | Future insight type adds a new payload prefix without updating the handler | Not covered — pre-existing gap, out of scope for this plan | Falls through, no-op (`if` chain, no `else`) | Card's action button silently does nothing — **not a new regression, but worth a follow-up TODO if a 3rd payload type is ever added** |

No critical gaps (no path found with zero test AND zero error handling AND a silent failure that's new to this plan) — the one silent no-op above is a pre-existing behavior, not introduced here.
